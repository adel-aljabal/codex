# تحليل مستودعات GitHub المرشحة لمنظومة SIRAJ

**التاريخ:** 2026-09-20  
**الحساب:** [adel-aljabal](https://github.com/adel-aljabal)  
**الغرض:** تقييم المستودعات الظاهرة في الصور وتحديد ما يفيد SIRAJ OS / SIRAJ ATLAS وما يجب تأجيله أو عزله.

> هذا تقرير تقييم، وليس موافقة تلقائية على تثبيت أي مشروع أو تمرير مفاتيح API إليه.

## الخلاصة التنفيذية

أفضل ثلاث مواد للاعتماد الآن هي:

1. **addyosmani/agent-skills** لاستخلاص دورة عمل موحدة للوكلاء: تعريف → تخطيط → بناء → اختبار → مراجعة → إطلاق.
2. **coleam00/context-engineering-intro** لبناء حزمة سياق مشتركة تمنع عمل كل وكيل بمعزل عن الآخرين.
3. **microsoft/ai-agents-for-beginners** كمرجع منظم للذاكرة، تعدد الوكلاء، البروتوكولات، الأمان، والوكلاء المحليين.

أما **abi/screenshot-to-code** فهو مفيد لاحقًا كخدمة اختيارية داخل SIRAJ ATLAS لتحويل لقطات الواجهات إلى نماذج أولية، لكنه ثقيل ويعتمد على مزودي نماذج ومفاتيح خارجية للحصول على أفضل نتيجة.

مستودعات **cporter202** الخاصة بقوائم APIs مفيدة كفهارس للبحث والانتقاء فقط. لا ينبغي استيرادها كلها ولا اعتبار عبارة “production-ready” ضمانًا؛ الروابط تحتاج تدقيقًا مستقلًا للأسعار، الخصوصية، الاستمرارية، وشروط الاستخدام، كما أن بعض الروابط تحمل تتبع إحالة تجاريًا.

## الشرح التفصيلي

### 1) Agent Skills

المستودع يضع مهارات قابلة للاكتشاف من عدة وكلاء، ويقسم العمل إلى مراحل واضحة: **Spec, Plan, Build, Test, Review, Ship**. أهم قيمة لنا ليست تثبيت 25 مهارة دفعة واحدة، بل اعتماد عقد تشغيل موحد:

- كل مهمة تبدأ بمواصفة ومعايير قبول.
- تتحول إلى خطوات صغيرة يمكن استئنافها.
- كل خطوة تنتج أثرًا قابلًا للتحقق.
- الاختبارات دليل الإنجاز.
- التوقف إلزامي عند الفشل أو العملية عالية الخطورة.
- التسليم يمر ببوابة مراجعة، وليس بمجرد إعلان الوكيل أنه انتهى.

**التطبيق المقترح:** تحويل هذه المبادئ إلى SIRAJ Task Contract مشترك، ثم السماح لكل جهاز بتنفيذ جزء محدد مع الكتابة في Event Ledger وFlight Recorder.

### 2) Context Engineering Intro

الفكرة الأساسية أن ضعف الوكيل غالبًا سببه نقص السياق، لا ضعف النموذج. المستودع يستعمل:

- ملف قواعد عام.
- وصف أولي للميزة.
- أمثلة مرجعية.
- وثائق وروابط.
- PRP مفصل.
- حلقات تحقق وإصلاح.

**التكييف المطلوب لـ SIRAJ:** بدل ملفات مرتبطة بـ Claude فقط، ننشئ تنسيقًا محايدًا يستطيع Codex وHermes وOpenClaw وGemini قراءته. الحزمة المقترحة لكل مهمة:

```text
task/
├── TASK.md
├── CONTEXT.md
├── ACCEPTANCE.md
├── PLAN.md
├── STATUS.json
├── evidence/
└── handoffs/
```

هذا هو الحل العملي لمشكلة عمل كل نموذج وحده: جميع الوكلاء يقرأون الحزمة نفسها، يكتبون تقدمهم في الحالة نفسها، ولا يبدأ وكيل خطوة قبل أن تكون تبعياتها مثبتة.

### 3) Microsoft AI Agents for Beginners

مرجع واسع يغطي تصميم الوكلاء، استعمال الأدوات، Agentic RAG، الوكلاء الموثوقين، التخطيط، تعدد الوكلاء، ما وراء المعرفة، الإنتاج، MCP/A2A/NLWeb، هندسة السياق، الذاكرة، التصفح، النشر، التشغيل المحلي، والأمان.

**القيمة:** يصلح لبناء قائمة تحقق معمارية لـ SIRAJ v0.4 وما بعدها.  
**القيد:** أمثلة كثيرة تتمحور حول Microsoft Foundry/Azure، لذلك نعتمد المفاهيم ونستبدل الخدمات السحابية بمكوناتنا المحلية أو مزودينا المعتمدين حيث يلزم.

### 4) VibeTags

بحسب وصف المستودع، هو annotation processor في Java يضيف حواجز لسلوك أدوات توليد الكود مثل Cursor وClaude وGemini وCodex CLI، مع مجلدات خاصة بهذه الأدوات.

**القيمة:** يثبت إمكانية وضع قيود قريبة من الكود بدل الاعتماد على التعليمات النصية فقط.  
**الحد:** SIRAJ متعدد اللغات وليس مشروع Java فقط؛ كما أن الانتشار المحدود للمستودع يعني أن علينا تقييم النضج، الاختبارات، الترخيص، وطريقة تجاوز القيود قبل الاعتماد.

**المقترح:** نقل الفكرة إلى Policy-as-Code داخل Approval Gate، وليس فرض المكتبة على جميع مكونات SIRAJ.

### 5) Screenshot-to-Code

يدعم HTML/Tailwind وHTML/CSS وReact/Vue وBootstrap وIonic، ويشغّل واجهة React/Vite وخلفية FastAPI. التشغيل المحلي يتطلب مفتاح مزود واحد على الأقل، بينما استخراج الأصول والفيديو وبعض خصائص الصور تعتمد أكثر على Gemini وReplicate.

**الاستخدام المناسب:** مولّد أولي لواجهات ATLAS، ثم مراجعة الكود وإدخاله في النظام عبر PR.  
**المخاطر:** إرسال لقطات قد تحتوي بيانات حساسة إلى مزود خارجي؛ اختلاف جودة الكود؛ تكلفة المفاتيح؛ وتغيّر قائمة النماذج.  
**القرار:** sandbox منفصل، بيانات تجريبية فقط، ولا وصول مباشر إلى مستودع الإنتاج.

### 6) قوائم API من cporter202

تشمل قوائم OpenClaw، الكشط، SEO، والتسويق. اثنان من المستودعات الحديثة يقدمان أرقامًا كبيرة مثل 903 API للـSEO و290 API للتسويق، لكن العدد لا يساوي الجودة.

**طريقة الاستخدام الصحيحة:**

1. اختيار حالة استخدام محددة.
2. استخراج 3–5 مزودين فقط.
3. التحقق من المصدر الرسمي، السعر، الحدود، الخصوصية، التغطية الجغرافية، وشروط إعادة البيع.
4. اختبار Adapter موحد بمفتاح تجريبي محدود.
5. تسجيل latency/cost/error-rate في ATLAS.
6. اعتماد مزود أساسي وآخر احتياطي بعد موافقة المالك.

**تنبيه:** وجود روابط إحالة في القوائم يعني أن الترتيب قد لا يكون محايدًا بالكامل.

### 7) Face Recognition

مكتبة Python معروفة مبنية على dlib، وتعرض كشف الوجوه والمعالم والترميز والمقارنة. إلا أن README يشير إلى أن Windows غير مدعوم رسميًا، كما تظهر إشارات توافق قديمة مثل Python 2.7/3.3+.

**لماذا لا نعتمدها الآن:** بيانات الوجه حساسة جدًا، والدمج على أجهزة Windows قد يكون صعبًا، والمشروع لا يعالج وحده الموافقة، التحيز، منع الانتحال، إدارة القوالب الحيوية، أو متطلبات الاستخدام المؤسسي. أي مشروع حقيقي يحتاج مراجعة قانونية وأمنية منفصلة.

## ما الذي نعتمده داخل SIRAJ الآن؟

### A. Shared Task Contract

كل مهمة طويلة تحصل على معرف ثابت وحزمة ملفات مشتركة. يحدد Router الوكيل المناسب حسب القدرة والجهاز، لكن الحقيقة التشغيلية تبقى في Core API/Event Ledger، لا في ذاكرة محادثة منفردة.

### B. Capability Registry

نسجل لكل وكيل:

- الجهاز والحالة.
- النموذج والمزود.
- الأدوات والمهارات.
- نوع المهام المناسبة.
- التكلفة والمهلة.
- القيود ومجال الصلاحية.
- آخر اختبار ناجح.

### C. Quality Gates

التدفق المعتمد:

```text
Intake → Context Pack → Plan → Owner/Risk Gate → Execute → Test → Review → Evidence → Merge/Release
```

### D. Research vs Runtime

- **Research Catalog:** قوائم API، الدورات، والمشاريع المرشحة.
- **Quarantine/Sandbox:** اختبار المشاريع الخارجية دون أسرار إنتاج.
- **Approved Components:** لا يدخلها مشروع إلا بعد الترخيص، الأمان، الاختبار، والملاءمة.
- **Runtime:** مكونات SIRAJ المراقبة عبر ATLAS.

## خطة التنفيذ المقترحة

1. اعتماد Task Contract موحد مستلهم من Agent Skills وContext Engineering.
2. إضافة حقول Agent/Device/Dependency/Evidence إلى Flight Recorder في ATLAS v0.4.
3. إنشاء `research/catalog.yaml` للفهرسة فقط، دون تثبيت تلقائي.
4. اختيار خمس مهارات كحد أقصى للموجة الأولى: spec، plan، test، review، ship.
5. بناء Adapter تجريبي واحد فقط من قوائم API بعد تحديد منتج دخل واضح.
6. إبقاء screenshot-to-code وface_recognition خارج قلب النظام حتى نجاح مراجعة منفصلة.

## ضوابط قبل استيراد أي مستودع

- مراجعة الترخيص وملفات SECURITY/CONTRIBUTING.
- تثبيت commit محدد بدل تتبع الفرع المتحرك مباشرة.
- فحص dependencies وGitHub Actions وinstall scripts.
- عدم تمرير مفاتيح إنتاج أثناء التجربة.
- منع الصلاحيات الواسعة والكتابة التلقائية إلى الفروع الأساسية.
- اختبار داخل بيئة معزولة مع سجل أدلة.
- موافقة المالك قبل الدمج أو تغيير المزود أو المفاتيح.

## النتيجة

هذه المجموعة لا تشكل “نظامًا واحدًا” جاهزًا، لكنها تقدم ثلاث طبقات نافعة:

- **تشغيل الوكلاء:** Agent Skills + Context Engineering.
- **التعلم والتحقق المعماري:** Microsoft AI Agents.
- **اكتشاف قدرات مستقبلية:** API lists + Screenshot-to-Code.

أفضل قرار حالي هو **دمج الأفكار والأنماط أولًا** داخل SIRAJ، لا تثبيت جميع المستودعات. هذا يحافظ على المعمارية الموحدة ويمنع رجوع كل نموذج للعمل منفردًا.
