**المشروع المستهدف:** SIRAJ OS / SIRAJ ATLAS

## 1. النتيجة التنفيذية

تضم الصور عشرة مستودعات، لكن اثنين منها سبق تحليلهما:

- `cporter202/openclaw-api-list`
- `cporter202/social-media-scraping-apis`

لذلك يوجد **ثمانية اكتشافات جديدة**.

أقوى النتائج لهذه الدفعة:

1. **LEANN** هو المرشح الأكثر ارتباطًا بذاكرة SIRAJ المحلية والبحث في الملفات، لكنه محرك فهرسة واسترجاع وليس بديلًا كاملًا للذاكرة أو Mem0 أو Event Ledger.
2. **ECC** يحتوي أفكارًا قوية جدًا لتنسيق الوكلاء والاختبار والمراجعة والذاكرة والأمان، لكنه ضخم للغاية: 68 وكيلًا و292 مهارة وفق README. تثبيته كاملًا سيكرر وظائف SIRAJ وقد يربك Hermes وCodex وOpenClaw. الأفضل دراسة AgentShield وCore Profile أولًا داخل Sandbox.
3. **n8n** مناسب كواجهة مرئية لأتمتة الأعمال والموصلات، لا كنواة لوكلاء SIRAJ. يجب وضعه خارج Core وربطه عبر API/Event Bus إذا تم اعتماده.
4. **Codex** هو الوكيل الرسمي الأقرب لدور المنسق/المهندس الحالي، بينما **OpenCode** بديل مفتوح متعدد المزودين. تشغيلهما مع Hermes وOpenClaw كقادة متوازيين سيعيد مشكلة “كل وكيل يعمل وحده”، لذلك يبقى SIRAJ Router هو صاحب توزيع الأدوار.
5. **Anthropic Skills** يقدم نمطًا معياريًا ممتازًا لبناء المهارات، لكن بعض مهارات المستندات source-available وليست مفتوحة المصدر. نأخذ المواصفة والأنماط مع احترام ترخيص كل مجلد.
6. **Generative AI Arbitrage** صفحة تسويق شبه كاملة لمزود واحد وروابط إحالة، وليس دراسة مستقلة للسوق. لا يعتمد كمصدر أسعار أو كمسار إنتاج.
7. مستودعات Lead Gen وSocial Scraping يمكن أن تفيد مسار الدخل، لكنها تحمل مخاطر خصوصية وشروط منصات وبيانات شخصية؛ لا تدخل Core ولا تنفذ آليًا دون سياسة امتثال.

## 2. فصل الطبقات

المستودعات لا تؤدي الدور نفسه:

| الطبقة | المشاريع | الدور الصحيح |
|---|---|---|
| Coding Harness | Codex، OpenCode، ECC | تنفيذ البرمجة، التخطيط، المراجعة والاختبار |
| Skills | Anthropic Skills، ECC Skills | تعليم الوكلاء إجراءات قابلة للتكرار |
| Workflow Automation | n8n، OpenClaw lists | ربط الخدمات وتشغيل تدفقات الأعمال |
| Retrieval/Memory | LEANN | فهرسة واسترجاع دلالي محلي |
| Provider Discovery | Generative AI Arbitrage | مقارنة مزودين بصورة أولية فقط |
| Revenue/Data Sources | Best APIs for Lead Gen، Social Scraping | أفكار وخدمات بيانات خارج Core |

القرار المعماري: **SIRAJ Core يبقى مصدر الحقيقة والمنسق الوحيد**. هذه المشاريع توضع خلف Adapters أو تستخدم كمراجع، ولا تتحول إلى مراكز قيادة متوازية.

# 3. تحليل كل مستودع

## 3.1 [StarTrail-org/LEANN](https://github.com/StarTrail-org/LEANN)

### ما هو؟

قاعدة/فهرس متجهي محلي للـRAG يعتمد إعادة حساب embeddings عند الطلب مع graph pruning بدل تخزين كل المتجهات بالطريقة التقليدية. يدعي المشروع توفيرًا يصل إلى 97% من مساحة التخزين مع المحافظة على الدقة، ويعرض benchmark قابلًا لإعادة التشغيل.

يدعم:

- الملفات والمستندات.
- البريد وسجل المتصفح والمحادثات.
- مستودعات الكود.
- MCP.
- Windows وLinux وmacOS.
- تكامل OpenClaw ضمن `skills/leann-memory`.

### لماذا هو مهم لنا؟

لدى SIRAJ ثلاثة أنواع بيانات مختلفة:

1. **Event Ledger:** ماذا حدث ومتى؟
2. **Memory/Knowledge:** ما الحقائق والقرارات التي يجب تذكرها؟
3. **Semantic Retrieval:** أي الملفات والمقاطع ترتبط بالسؤال الحالي؟

LEANN يخدم النوع الثالث أساسًا. لذلك يمكن أن يكمل Mem0 وSQLite ولا يستبدلهما.

### أين يمكن استخدامه؟

- البحث في مستودعات ASUS وSamsung دون رفع الملفات للسحابة.
- استرجاع تقارير العمل والملاحظات الفنية.
- إيجاد أجزاء الكود ذات الصلة قبل أن يبدأ الوكيل بالتعديل.
- تقليل تكرار المسح الكامل للمستودع واستهلاك السياق.

### القيود العملية

- بناء Windows من المصدر يحتاج Visual Studio 2022 Build Tools وCMake وSWIG وvcpkg ومكتبات C++.
- الجهاز ASUS وصل سابقًا إلى 93.3% RAM، لذلك لا نبدأ بفهرسة ضخمة.
- Samsung لديه مشكلة WSL سابقة، فلا نجعله أول منصة للتجربة.
- ادعاء 97% هو نتيجة المشروع ويجب إعادة قياسه على بياناتنا.
- الفهرس الصغير لا يلغي وقت embedding/recomputation ولا سياسات الحذف والصلاحيات.

### القرار

**مرشح Pilot قوي، وليس تثبيتًا فوريًا.**

اختبار مقترح:

- مجلد واحد غير حساس.
- 500–2,000 ملف كحد أولي.
- مقارنة مع `rg` وBM25 والطريقة الحالية.
- قياس recall والمهلة والذاكرة وحجم الفهرس واستهلاك CPU.
- عدم فهرسة مفاتيح أو ملفات `.env` أو بيانات وظيفية حساسة.

**الأولوية: عالية بعد تجميد ATLAS v0.4.**

## 3.2 [affaan-m/ECC](https://github.com/affaan-m/ECC)

### ما هو؟

نظام تشغيل/حزمة تشغيل للوكلاء البرمجيين. دورة العمل المعلنة:

```text
plan → test → implement → review → verify → remember → improve
```

يدعم Claude وCodex وKimi، ويوفر Adapters متفاوتة القدرات لـCursor وOpenCode وGemini وKiro وHermes وOpenClaw وغيرها. يحتوي وفق README على:

- 68 وكيلًا.
- 292 مهارة.
- 94 command shim.
- hooks وmemory وcontinuous learning.
- AgentShield لفحص prompts وMCP والصلاحيات والأسرار وملفات الوكلاء.

### ما الفائدة الحقيقية؟

المشروع قريب جدًا من هدف SIRAJ التشغيلي: منع الوكيل من القفز إلى التنفيذ، حفظ السياق، الاختبار، المراجعة من سياق جديد، وتحويل النجاحات المتكررة إلى Skills.

### أين يتداخل مع SIRAJ؟

| ECC | SIRAJ |
|---|---|
| Agents | Agent Router/Workers |
| Memory | Memory Core + Mem0 |
| Hooks | Governance/Approval Gate |
| Continuous learning | Optimization Loop |
| Skills | Capability Registry |
| AgentShield | Security/Policy Scanner |
| Multi-harness adapters | SIRAJ Fabric/Bridge |

التثبيت الكامل قد يصنع **نظام تشغيل داخل نظام التشغيل** ويجعل من الصعب تحديد صاحب القرار أو مصدر الحقيقة.

### مخاطر الدمج الكامل

- مئات المهارات قد توسع السياق وتزيد التعارض.
- hooks قد تغير سلوك Codex/Hermes/OpenClaw بصورة غير متوقعة.
- مستويات الدعم ليست متساوية بين الـharnesses.
- التشغيل عبر npm ينفذ كود تثبيت؛ تثبيت الإصدار لا يعادل تدقيقًا أمنيًا.
- الذاكرة المستقلة قد تتعارض مع ذاكرة SIRAJ.
- تحديثات المشروع قد تغير القواعد تلقائيًا إذا لم نثبت commit محددًا.

### القرار

لا نثبت ECC عالميًا الآن. ننشئ تقييمًا من ثلاث مراحل:

1. مراجعة `AgentShield` وقواعد فحص الأسرار والصلاحيات.
2. مقارنة `core profile` مع Shared Task Contract الذي اعتمدناه.
3. تجربة على مستودع مؤقت بلا مفاتيح، مع `dry-run` حيث يتوفر.

ما ينجح يُعاد تنفيذه داخل SIRAJ أو يوضع خلف Adapter.  
**الأولوية: عالية كمرجع أمني وتشغيلي، متوسطة كاعتمادية مباشرة.**

## 3.3 [n8n-io/n8n](https://github.com/n8n-io/n8n)

### ما هو؟

منصة visual workflow automation مع كود JavaScript/Python وقدرات AI وhuman approvals وobservability وأكثر من 1,500 integration وآلاف القوالب. يمكن تشغيلها ذاتيًا أو سحابيًا.

### ما الذي يمكن أن تضيفه؟

- واجهة رسومية يفضلها المستخدم بدل الاعتماد الدائم على الطرفية.
- بناء تدفقات Gmail/Drive/GitHub/Notion وغيرها.
- webhooks وschedules وربط الخدمات.
- موافقة بشرية ضمن التدفقات.
- رؤية واضحة للخطوات ونتائج كل node.

### ما الذي لا ينبغي أن تصبحه؟

لا ينبغي أن تحل محل:

- Core API.
- Event Ledger.
- Agent Router.
- Approval Gate.
- ATLAS.

n8n ممتاز في **أتمتة الأعمال والموصلات**، لكنه ليس المصدر الصحيح لذاكرة SIRAJ أو قرارات الوكلاء.

### موضعه المقترح

```text
SIRAJ Core → signed task/webhook → n8n workflow
n8n result → evidence event → SIRAJ Event Ledger
```

أي أن SIRAJ يقرر، وn8n ينفذ تدفقات تكامل محددة.

### القيود

- الترخيص Fair-code/Sustainable Use License وليس ترخيص Open Source تقليديًا لكل الاستخدامات التجارية.
- تشغيل Docker وخدمات إضافية على ASUS قد يزيد ضغط RAM.
- بيانات الاعتماد في n8n تحتاج تشفيرًا ونسخًا احتياطيًا وفصل بيئات.
- لا ننفذ `curl | sh` قبل مراجعة السكربت.
- آلاف القوالب لا تعني أنها آمنة أو حديثة.

### القرار

**مرشح قوي للمرحلة التجارية وواجهات الأتمتة، لكنه مؤجل حاليًا حتى استقرار ATLAS وربط الأجهزة.** عند التجربة يبدأ Workflow واحد read-only، وليس تثبيتًا واسعًا.

## 3.4 [openai/codex](https://github.com/openai/codex)

### ما هو؟

وكيل برمجة رسمي من OpenAI يعمل محليًا عبر CLI، وله تكامل IDE وتجربة تطبيق، ويمكن استخدامه عبر تسجيل ChatGPT أو API.

### دوره المناسب في SIRAJ

- المهندس والمنسق عالي القدرة.
- مراجعة التغييرات الحرجة.
- بناء الخطط وعقود العمل.
- تنفيذ مهام داخل مستودعات محددة وفق Approval Gate.
- حفظ evidence وhandoffs للوكلاء الآخرين.

### لماذا لا ننسخ المستودع داخل نظامنا؟

نحن نستخدم المنتج/الوكيل، ولا نحتاج fork ضخم للمصدر ما لم توجد مساهمة أو تعديل محدد. تتبع المصدر الكامل سيضيف عبء تحديث وأمان وبناء Rust بلا فائدة مباشرة.

### العلاقة مع Hermes وOpenClaw

- **Codex:** تخطيط وبرمجة ومراجعة معقدة.
- **Hermes:** harness محلي/واجهة على ASUS وتنفيذ المهام الموجهة.
- **OpenClaw:** تشغيل وأتمتة وأدوات.
- **النماذج المحلية:** مهام منخفضة التكلفة، تصنيف، تلخيص، معالجة خاصة.
- **SIRAJ Router:** يحدد من يعمل ولا يسمح بالتنافس على المهمة نفسها.

### القرار

يبقى Codex أداة أساسية، لكن كل مهمة طويلة يجب أن تخرج إلى Shared Task Contract وFlight Recorder حتى لا تضيع عند انتهاء الجلسة أو الرصيد.

## 3.5 [anomalyco/opencode](https://github.com/anomalyco/opencode)

### ما هو؟

وكيل برمجة مفتوح المصدر متعدد المنصات، متوفر كطرفية وتطبيق Desktop تجريبي. لديه:

- وكيل `build` بصلاحيات كاملة.
- وكيل `plan` للقراءة والتحليل.
- subagent عام.
- تعدد مزودين وإعدادات مرنة.
- واجهة عربية موثقة.

### نقاط القوة

- حياد أكبر تجاه مزود النموذج.
- خطة قراءة فقط مقابل بناء.
- تطبيق Desktop يتوافق مع تفضيل المستخدم للواجهات.
- مشروع واسع ونشط.

### نقاط الضعف في سياقنا

- لدينا بالفعل Codex وHermes وOpenClaw وxKiro؛ إضافة قائد خامس لن تحل مشكلة التنسيق.
- وضع build الكامل يحتاج حوكمة واضحة.
- التطبيق Desktop ما زال Beta.
- جلسة OpenCode web السابقة طالت وتسببت في صعوبة اللصق، لذلك التجربة الحالية ليست سببًا كافيًا لجعله الأساس.
- التثبيت السريع عبر pipe-to-shell ليس المسار المفضل لدينا.

### القرار

يبقى **عاملًا احتياطيًا Provider-neutral**، لا نستخدمه كمنسق رئيسي. إذا جُرّب، يبدأ Plan/read-only على نسخة غير حساسة مع تسجيل النتائج في SIRAJ.

## 3.6 [anthropics/skills](https://github.com/anthropics/skills)

### ما هو؟

تنفيذ Anthropic لمعيار Agent Skills. كل Skill مجلد مستقل يحتوي `SKILL.md` مع frontmatter يحدد الاسم والوصف، ثم التعليمات والأمثلة والموارد والسكربتات.

### القيمة لـSIRAJ

- Progressive disclosure: تحميل المهارة عند الحاجة بدل وضع كل شيء في السياق.
- قابلية نقل المهارات بين أدوات مختلفة إذا التزمنا معيارًا محايدًا.
- فصل المعرفة الإجرائية عن النموذج والمزود.
- إمكان versioning والاختبار والمراجعة في Git.

### تنبيه الترخيص

README يوضح أن كثيرًا من المهارات Apache 2.0، لكن مهارات DOCX/PDF/PPTX/XLSX **source-available وليست open source**. لذلك لا يجوز افتراض أن كل مجلد له شروط الترخيص نفسها أو نسخه داخل منتج تجاري بلا مراجعة.

### ما نعتمده؟

صيغة SIRAJ Skill Package المقترحة:

```text
skill-name/
├── SKILL.md
├── manifest.json
├── scripts/
├── references/
├── tests/
└── SECURITY.md
```

ويضاف:

- النطاق والصلاحيات.
- الموصلات المطلوبة.
- مستوى الخطورة.
- الأجهزة المتوافقة.
- الاختبارات.
- hash للمصدر.
- الترخيص لكل مكوّن.

### القرار

**اعتماد المعيار كنمط، وعدم نسخ كل المهارات.** نستخرج فقط المهارات التي نحتاجها ونبني نسخًا خاصة بـSIRAJ حيث يلزم.

## 3.7 [cporter202/generative-ai-arbitrage](https://github.com/cporter202/generative-ai-arbitrage)

### ما هو فعليًا؟

README صغير يروّج لمسار API موحد عبر Kie.ai لتوليد الفيديو والصور والموسيقى، مع مقارنات أسعار وروابط إحالة. حجم المستودع صغير ولا يمثل benchmark أو SDK مستقلًا.

### لماذا يجب الحذر؟

- الأسعار سريعة التغير ولا تُعتمد من لقطة قديمة.
- “نفس النموذج” عبر وسيط يحتاج تحققًا من provenance والإصدار والشروط.
- لا نعرف من README وحده سياسة الاحتفاظ بالمدخلات والمخرجات.
- uptime والتوفير ادعاءات تسويقية وليست قياسات مستقلة.
- الوسيط الموحد يقلل عدد المفاتيح لكنه يزيد single-vendor dependency.
- المحتوى الحساس أو صور العمل لا ترسل إلى وسيط غير مدقق.

### متى قد يفيد؟

فقط لتجربة وسائط غير حساسة بميزانية صغيرة إذا احتجنا توليدًا لا يتوفر محليًا، بعد:

- مراجعة الشروط والخصوصية.
- اختبار جودة output.
- وضع حد إنفاق.
- عدم استخدام مفاتيح أو بيانات إنتاج.
- مقارنة التكلفة الفعلية مع المصدر الرسمي وقتها.

### القرار

**مرجع أسعار غير موثوق زمنيًا؛ لا يدخل Router تلقائيًا ولا يصبح fallback.**

## 3.8 [cporter202/best-apis-for-lead-gen](https://github.com/cporter202/best-apis-for-lead-gen)

### ما الفرق عن مستودع Lead Gen السابق؟

هذا المستودع أكثر تنظيمًا: 30 API منتقاة، 10 workflows، 10 playbooks، 12 فئة، مع استخدامات مثل:

- الشركات المحلية.
- إشارات التوظيف.
- enrichment.
- المراجعات.
- الشركات الناشئة.
- التجارة والعقار.

هو أفضل للبحث من القائمة ذات “3,452 API”، لكنه يظل دليلًا تجاريًا لا تنفيذًا موثوقًا.

### فرصة مناسبة لنا

بدل جمع بريد وأرقام أشخاص، نبدأ بمنتج أقل مخاطرة:

**Local Business Intelligence Brief**

- بيانات أعمال عامة.
- مراجعات ومشكلات متكررة.
- ظهور محلي ومقارنة منافسين.
- تقرير عربي/إنجليزي.
- لا إرسال تلقائي ولا تخزين واسع لبيانات شخصية.

بعد إثبات طلب فعلي يمكن إضافة enrichment قانوني ومحدود.

### ضوابط لازمة

- مصدر كل حقل ووقت جمعه.
- حق الحذف والتصحيح.
- عدم تخمين البريد أو الهوية.
- عدم إرسال outreach بلا موافقة.
- احترام قوانين قطر وشروط المنصات.
- فصل بيانات العملاء عن بيانات التجربة.

### القرار

**مفيد لمسار الدخل، لا لقلب SIRAJ.**

## 3.9 المستودعات المكررة: OpenClaw API List وSocial Media Scraping APIs

### OpenClaw API List

التصنيفات الكبيرة — agents وAI وautomation وbusiness وdeveloper tools وMCP وغيرها — هي فهارس. وجود مجلدات بعدد كبير لا يثبت:

- أن كل API يعمل.
- أنه رسمي.
- أنه آمن.
- أنه يسمح بإعادة البيع.
- أنه متوافق مع OpenClaw الحالي.

يجب تحويله إلى **Candidate Catalog** فقط، ثم يمر كل مزود عبر Vendor Gate.

### Social Media Scraping APIs

# 5. البنية المقترحة بعد هذه الدفعة

```text
Owner
  ↓
SIRAJ Core / Approval Gate
  ↓
Agent Router
  ├─ Codex: architecture, difficult coding, review
  ├─ Hermes: local execution on ASUS
  ├─ OpenClaw: tools and scheduled execution
  ├─ Local Models: low-cost private tasks
  └─ OpenCode: optional backup
  ↓
Task Bus + Event Ledger
  ├─ ATLAS / Flight Recorder
  ├─ LEANN Retrieval Adapter
  └─ n8n Business Workflow Adapter
```

- ECC وAnthropic Skills يغذيان طبقة السياسات والمهارات.
- قوائم APIs تغذي Research Catalog فقط.
- لا توجد أداة خارجية تكتب مباشرة في الذاكرة أو الفرع الأساسي دون Core.

# 6. خطة تنفيذ واقعية

## المرحلة A — لا تغييرات تشغيلية

1. تسجيل المستودعات في Candidate Catalog.
2. تثبيت commit SHA لكل مرجع.
3. توثيق الترخيص والمخاطر.
4. عدم تثبيت n8n أو ECC أو LEANN على الأجهزة الآن.

## المرحلة C — الأتمتة التجارية

1. تجربة n8n مع Workflow read-only واحد.
2. بناء Local Business Intelligence Brief.
3. تشغيله يدويًا لعميل تجريبي قبل SaaS.
4. قياس تكلفة البيانات والزمن وجودة التقرير.
5. تحويل الأجزاء المثبتة فقط إلى أتمتة.

# 7. قائمة المنع الحالية

- لا `curl | bash` أو `irm | iex` لمشروعات غير مدققة.
- لا Full Access لوكيل جديد.
- لا نسخ شامل لمئات المهارات.
- لا فهرسة أسرار وملفات `.env`.
- لا fallback جديد أو تغيير xKiro/Endpoint/API/Default Provider.
- لا إرسال بيانات حساسة إلى مجمع API رخيص.
- لا scraping لبيانات شخصية أو محتوى محمي دون أساس مشروع.
- لا تثبيت خدمة ثقيلة على ASUS أثناء ضغط الذاكرة.
- لا إضافة Orchestrator آخر ينافس SIRAJ Core.

# 8. الحكم النهائي

أفضل ما يستحق البناء عليه:

1. **LEANN** كـRetrieval Adapter محلي بعد اختبار صغير.
2. **ECC AgentShield** كمصدر لقواعد الفحص، لا كمنظومة كاملة.
3. **Anthropic Agent Skills specification** لتوحيد حزم المهارات.
4. **n8n** لاحقًا كطبقة أتمتة أعمال مرئية خارج Core.
5. **Codex** يظل المهندس والمنسق، مع إلزامه بـShared Task Contract.
6. **OpenCode** احتياطي فقط.
7. **Lead Gen** يتحول إلى منتج تقارير أعمال عامة، لا ماكينة جمع بيانات شخصية.
8. **Generative AI Arbitrage** لا يعتمد إلا كتجربة وسائط غير حساسة بعد تحقق مستقل.

الخلاصة الأهم: القوة لن تأتي من تثبيت أكبر عدد من الأدوات، بل من وضع كل أداة في طبقتها الصحيحة، ومنع تعدد مصادر الحقيقة، وقياس كل إضافة قبل إدخالها إلى Runtime.
